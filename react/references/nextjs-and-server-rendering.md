# Next.js and server rendering

- Identify the router and installed Next.js version. Use its actual routing, data, caching, and deployment conventions. In App Router projects, keep server-owned reads and secrets on the server. Introduce client entry points for interactive state, effects, or browser APIs, and pass values supported across the React Server Component boundary. Keep client imports narrow and preserve existing providers and layout ownership.
- Place pending, error, and not-found UI at useful route or subtree boundaries. When streaming supported data under Suspense, choose boundaries that let useful content appear independently. Start independent requests early when safe. Maintain intended prefetch, navigation, and mutation feedback.
- Determine cache scope and invalidation from the installed framework and the data contract. Check per-request deduplication, persistent caching, and route/client caching independently. Keep user-scoped reads and cache keys isolated. Replay invalidation through navigation, refresh, and a fresh session as appropriate.
- Validate and authorize server mutations using existing application controls. Return expected validation issues to the form, apply the appropriate invalidation, and verify duplicate and failed submissions. Keep server-only credentials and implementation details out of client modules and serialized data.
- To debug hydration, compare the server HTML with the first client render under the same initial data. Inspect invalid markup, clocks, locale/timezone differences, IDs, browser-only APIs, storage-derived defaults, and changing external data. Use deterministic initial markup or a framework-supported client-only boundary when necessary. Reserve hydration suppression for a deliberate isolated mismatch.
- For browser-stored preferences, start with a deterministic snapshot, then read and validate storage after hydration. Guard persistence until initialization completes so defaults cannot overwrite saved data. If the first paint must reflect preferences, use request-readable state when appropriate.
- Verify the production build and representative route paths, including a direct request, client navigation, and loading or mutation failure. Check the real deployment runtime if the change depends on environment support.

Official references [Server and Client Components](https://nextjs.org/docs/app/getting-started/server-and-client-components) and [Hydration](https://react.dev/reference/react-dom/client/hydrateRoot).
